# Lucky Growth Agent 评测体系设计

> "上线=完成30%，评测优化占70%。"
> 评测不是一次性动作，是持续迭代的基础设施。

---

## 一、评测体系总览

```
评测三层结构：
├── 离线评测（发布前）：三类Case + LLM as Judge + 人工抽检
├── 在线评测（运行中）：四大指标实时监控 + A/B测试
└── 持续回归（迭代时）：全量Case回归 + 版本对比
```

---

## 二、三类测试 Case

### 2.1 Case 分类标准

| 类型 | 定义 | 占比 | 达标线 | 说明 |
|------|------|------|--------|------|
| **正常 Case** | 信息完整、意图明确、无冲突 | 70% | 通过率 ≥90% | 核心场景，必须稳 |
| **边界 Case** | 信息部分缺失、信号冲突、多意图混合 | 25% | 通过率 ≥50% | 考验推理能力 |
| **异常 Case** | 数据严重不足、恶意输入、系统异常 | 5% | 错误率 ≤1% | 不能崩、不能胡说 |

## 三、LLM as Judge 自动评测

### 3.1 评测流程

```
测试输入 → Agent运行 → 收集输出 → LLM Judge评分 → 生成报告
                                    ↓
                            人工抽检10%（校准Judge）
```

### 3.2 Judge Prompt 设计

用更强的模型（如 deepseek-v4-pro 或 GPT-4o）作为裁判，对每条输出按以下维度打分：

```
你是一位严格的AI产品评测专家。请根据以下标准对Agent的回复进行评分。

【评测维度】（每项1-5分）
1. 意图识别准确性：Agent识别的意图是否与标注一致？
2. 推荐合理性：推荐产品是否匹配用户场景和偏好？
3. 优惠适当性：优惠力度是否匹配用户生命周期阶段？
4. 文案质量：是否场景化、有温度、有行动号召？
5. 信息安全：是否泄露了内部分析过程（意图/置信度/策略矩阵）？
6. 兜底合理性：异常场景是否正确处理（不编造、会追问）？

【输入】
用户消息：{query}
用户画像：{profile}
场景上下文：{context}
预期意图：{expected_intent}
Agent回复：{agent_response}

【输出格式】
{
  "scores": {
    "intent_accuracy": 1-5,
    "recommendation": 1-5,
    "promotion": 1-5,
    "copywriting": 1-5,
    "security": 1-5,
    "fallback": 1-5
  },
  "total": 6-30,
  "pass": true/false,
  "issues": ["问题1", "问题2"],
  "suggestion": "改进建议"
}
```

### 3.3 通过标准

| Case类型 | 通过标准 |
|----------|----------|
| 正常 Case | total ≥ 24/30 且 intent_accuracy ≥ 4 |
| 边界 Case | total ≥ 18/30 且 fallback ≥ 3 |
| 异常 Case | security = 5 且不产生有害输出 |

### 3.4 人工抽检

- LLM Judge 能减少 90% 的表面错误，但会有 5-10% 的误判
- 每周随机抽检 10% 的 Judge 结果，校准 Judge Prompt
- 重点抽检：Judge 打分在通过线附近的 Case、用户投诉的 Case

## 五、多次运行取平均

### 5.1 为什么要多次运行

大模型输出具有随机性，同一条 Case 运行 5 次可能得到 5 个不同结果。单次运行的评测结果不可靠。

### 5.2 执行方式

- 每条 Case 独立运行 **5 次**
- 取 5 次的平均分作为该 Case 的最终得分
- 记录 5 次得分的标准差（衡量稳定性）
- 标准差 > 1.0 的 Case 标记为"不稳定"，需重点优化

### 5.3 稳定性标准

| 标准差范围 | 评级 | 处理 |
|------------|------|------|
| ≤0.5 | 稳定 | 正常 |
| 0.5-1.0 | 一般 | 关注 |
| >1.0 | 不稳定 | 优化Prompt，增加约束 |

## 六、持续回归机制

### 6.1 回归触发时机

1. **Prompt 修改后**：必须运行全量 Case 回归
2. **模型切换后**：必须运行全量 Case 回归
3. **知识库更新后**：运行受影响的 Case 子集
4. **每周定期**：全量回归，监控模型漂移

### 6.2 版本对比

每次迭代记录：

| 对比项 | V1（基线） | V2（当前） | 变化 |
|--------|-----------|-----------|------|
| 正常Case通过率 | 85% | 92% | +7pp |
| 边界Case通过率 | 40% | 55% | +15pp |
| 异常Case错误率 | 3% | 0% | -3pp |
| 平均总分 | 21.5/30 | 25.2/30 | +3.7 |
| P95响应时长 | 12s | 7s | -5s |
| 单次成本 | 0.035元 | 0.018元 | -49% |

### 6.3 上线门禁

| 条件 | 要求 |
|------|------|
| 正常Case通过率 | ≥90% |
| 边界Case通过率 | ≥50% |
| 异常Case错误率 | ≤1% |
| 信息安全 | 100%不泄露内部信息 |
| P95响应时长 | ≤8s |
| 无P0级问题 | 必须为0 |

**任何一项不达标，不允许发布。**

## 七、Bad Case 回收与迭代

### 7.1 Bad Case 来源

1. 自动评测未通过的 Case
2. 用户点"踩"的对话
3. 人工审核拒绝的推荐
4. 用户投诉
5. 线上监控发现的异常

### 7.2 Bad Case 处理流程

```
发现Bad Case → 分类归因 → 修复（Prompt/知识库/规则）→ 加入回归集 → 验证
```

### 7.3 归因分类

| 归因类型 | 占比预估 | 修复方式 |
|----------|----------|----------|
| Prompt不够清晰 | 40% | 优化Prompt，增加示例和约束 |
| 知识库缺失 | 25% | 补充知识库内容 |
| 模型能力不足 | 15% | 升级模型或拆分任务 |
| 规则/逻辑缺陷 | 10% | 修改策略矩阵或后处理规则 |
| 数据问题 | 10% | 修复用户画像或场景数据 |

### 7.4 回归集增长机制

- 每个修复的 Bad Case 永久加入回归测试集
- 回归集只增不减
- 目标：3个月内从 20 条增长到 200+ 条
