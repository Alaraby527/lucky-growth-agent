# Lucky Growth Agent 成本优化方案

> 成本优化不是事后算账，是架构设计时就要考虑的约束。
> 目标：在保证效果的前提下，单次对话成本降低 60%+。

---

## 一、成本现状分析

### 1.1 当前架构 Token 消耗估算

| 节点 | 输入Token | 输出Token | 模型 | 单次成本估算 |
|------|-----------|-----------|------|-------------|
| 参数提取器 | ~200（系统提示+用户消息） | ~80 | deepseek-v4-flash | ~0.001元 |
| 策略分析 | ~4500（系统提示3994字+画像+知识库） | ~500 | deepseek-v4-flash | ~0.008元 |
| 回复生成 | ~500（策略分析结果+用户消息） | ~200 | deepseek-v4-flash | ~0.002元 |
| **合计** | **~5200** | **~780** | | **~0.011元/次** |

### 1.2 成本瓶颈

1. **策略分析节点输入过长**：系统提示词约4000字，每次都全量发送
2. **知识库结果全量传入**：Top5 文档片段可能包含大量无关内容
3. **三个节点串行调用模型**：参数提取+策略分析+回复生成，3次模型调用
4. **无缓存机制**：相同场景重复请求，每次都重新计算

---

## 二、成本优化五手段

### 2.1 模型分级（预计节省 40-50%）

**原则：用对的模型，不用贵的模型。弱模型处理80%简单任务，强模型只处理5%复杂任务。**

| 节点 | 当前模型 | 优化方案 | 理由 |
|------|----------|----------|------|
| 参数提取器 | deepseek-v4-flash | qwen-turbo（更便宜） | 提取任务简单，结构化输出，弱模型足够 |
| 策略分析 | deepseek-v4-flash | 分级路由（见下） | 高置信度简单场景用弱模型，复杂场景用强模型 |
| 回复生成 | deepseek-v4-flash | qwen-turbo | 文案生成有明确约束，弱模型足够 |
| LLM Judge | 无 | deepseek-v4-pro / GPT-4o | 评测需要强推理能力，但离线运行不影响线上成本 |

**策略分析分级路由：**

```
用户请求
    ↓
参数提取（qwen-turbo）
    ↓
快速判断复杂度（规则）
    ├── 简单场景（高置信度、有画像、信号一致）
    │   → qwen-turbo 直接生成策略（成本~0.002元）
    │
    ├── 中等场景（信号部分缺失、边界Case）
    │   → deepseek-v4-flash 生成策略（成本~0.008元）
    │
    └── 复杂场景（信号冲突、新用户、流失召回、异常）
        → deepseek-v4-pro 生成策略（成本~0.03元，但仅占5%）
```

**模型成本对比（估算）：**

| 模型 | 输入价格/百万Token | 输出价格/百万Token | 相对成本 |
|------|-------------------|-------------------|----------|
| qwen-turbo | ~0.3元 | ~0.6元 | 1x |
| deepseek-v4-flash | ~1元 | ~2元 | 3x |
| deepseek-v4-pro | ~8元 | ~16元 | 20x |

**加权平均成本：**
- 80% × 0.003元 + 15% × 0.011元 + 5% × 0.035元 = **0.0058元/次**
- vs 当前 0.011元/次，**节省约47%**

### 2.2 Prompt 缓存（预计节省 30-50% 输入Token）

**原理：** 系统提示词部分（约4000字）每次请求都相同，利用模型厂商的 Prompt Cache 功能，缓存命中部分只收 10-30% 费用。

**实施方式：**
- 将系统提示词放在 messages 数组最前面（固定不变）
- 动态内容（用户画像、知识库结果）放在后面
- 开启 DeepSeek / 通义千问的 Context Caching 功能

**缓存命中率预估：**
- 系统提示词 ~4000 Token，固定不变 → 命中率 100%
- 用户画像 ~200 Token，同一用户重复请求时命中
- 知识库结果 ~500 Token，相同查询时命中
- 综合输入 Token 节省：**约 60%**

**成本影响：**
- 策略分析节点输入成本降低 60%
- 整体成本再降 **约 20%**

### 2.3 结果缓存（预计节省 10-15%）

**原理：** 相同或高度相似的请求，直接返回缓存结果，不调用模型。

**缓存策略：**

| 缓存层级 | Key | TTL | 场景 |
|----------|-----|-----|------|
| 用户级缓存 | user_id + 时段 + 意图 | 2小时 | 同一用户相同时段重复请求（如反复打开APP） |
| 场景级缓存 | 意图 + 生命周期 + 天气类型 | 30分钟 | 相似场景的推荐结果复用 |
| 产品信息缓存 | 知识库文档hash | 24小时 | 菜单信息不频繁变化 |

**缓存规则：**
- 高置信度（≥80%）的推荐结果可缓存
- 中低置信度不缓存（需要实时分析）
- 优惠信息不缓存（可能实时变化）
- 缓存命中时记录日志，用于评估缓存合理性

### 2.4 并行节点（已实现）

当前架构中，代码执行（用户画像查询）和知识检索已经并行执行：

```
参数提取器 → ┌→ 代码执行（~0.5s）──┐
             └→ 知识检索（~1.5s）──┘→ 策略分析
```

**优化效果：** 总耗时从串行 2s 降为并行 1.5s，节省 0.5s。

**进一步优化：**
- 参数提取器与知识检索可以并行（知识检索直接用 sys.query，不需要等参数提取）
- 优化后：参数提取 + 知识检索 + 代码执行 三者并行

```
开始 → ┌→ 参数提取器（~1s）──┐
       ├→ 代码执行（~0.5s）──┤→ 策略分析
       └→ 知识检索（~1.5s）──┘
```

### 2.5 上下文压缩（预计节省 20-30% 输入Token）

**当前问题：** 策略分析节点接收全部知识库结果（Top5 文档片段），可能包含大量无关内容。

**压缩策略：**

1. **知识库结果压缩**
   - Rerank 后只传 Top3（而非 Top5）
   - 每个文档片段截断到最相关的 200 字
   - 预计从 ~800 Token 压缩到 ~400 Token

2. **用户画像压缩**
   - 代码节点只返回关键字段（姓名、等级、偏好Top3、客单价），不返回完整描述
   - 预计从 ~300 Token 压缩到 ~100 Token

3. **系统提示词精简**
   - 将 4000 字系统提示词拆分为"核心指令"（~1500字）和"详细规范"（~2500字）
   - 简单场景只传核心指令
   - 复杂场景传完整提示词

4. **对话历史裁剪**
   - 多轮对话只保留最近 3 轮
   - 更早的历史用摘要替代（"用户之前询问了美式，偏好大杯"）

|----------|-------------|----------|-----------|

## 四、成本监控看板

### 4.1 核心监控指标

| 指标 | 定义 | 告警阈值 |
|------|------|----------|
| 单次对话成本 | 总Token费用/对话次数 | >0.006元 |
| 模型调用分布 | 各模型调用占比 | 强模型占比>8% |
| 缓存命中率 | 缓存命中次数/总请求 | <30% |
| Token消耗趋势 | 日均Token消耗量 | 日环比增长>20% |
| 各节点Token占比 | 单节点Token/总Token | 策略分析>70% |

### 4.2 成本归因

当成本异常升高时，按以下维度归因：
1. **流量维度**：请求量是否异常增长
2. **模型维度**：强模型调用占比是否升高
3. **Token维度**：平均输入/输出Token是否增长
4. **缓存维度**：缓存命中率是否下降
5. **异常维度**：是否有重试/异常导致重复调用
